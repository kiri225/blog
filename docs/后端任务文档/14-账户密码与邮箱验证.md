# 14 — 账户密码与邮箱验证（规划）

本文件是**尚未实现**的规划，不是 `docs/modules/` 交接文档。代码落地后改 `docs/modules/01-用户认证.md`（仍是认证模块，不新开序号），并以代码为准。

前置：管理员 JWT 已完成（登录 / `GET/PUT /me`）。写法跟现有仓库：`Result` 信封 `code=200`、文件 PascalCase、`api` 不写 `session.exec`。

对照现状：`app/api/AuthRouter.py`、`app/service/AuthService.py`、`app/schemas/AuthSchemas.py`、`app/models/User.py`、`app/utils/JWTUtils.py`。管理后台在独立仓库 `../blog-app/admin`，入口 `/account-settings`。

---

## 1. 要做成什么样

单管理员后台：能改自己的登录密码；绑定或更换邮箱时必须先验证新邮箱。

| 角色 | 能做什么 |
|------|----------|
| 已登录管理员 | 用旧密码改新密码；向新邮箱收验证码，校验通过后写入 `user.email` |
| 未登录 | 不能改密、不能发码、不能换邮箱（本期不做「忘记密码」） |

### 1.1 为什么邮箱不能继续走 `PUT /me`

管理后台「个人信息」已经能把邮箱直接 `PUT /api/auth/me` 写进库，没有验证。做邮箱验证的同时必须**从 `PUT /me` 拿掉 `email`**，否则验证接口形同虚设。

### 1.2 本期不做

- 忘记密码 / 未登录重置
- 改密后作废当前 JWT（没有黑名单；72 小时自然过期）
- 密保手机、密保问题、安全日志、偏好通知
- Redis、验证码表、多管理员、改用户名
- 为 `EmailStr` 新增 `email-validator` 依赖

以后要加，写在文末「后续」，不要第一期塞进去。

## 4. 鉴权

三条新接口全部 **管理员 JWT**。无 Token → **403**；无效 / 过期 → **401** `无效的令牌`。用户已删 → **404** `用户不存在`。

GitHub 访客 Token 不能调这些接口（`get_current_user` 解的是管理员 JWT）。

---

## 5. 接口

前缀：`/api/auth`。成功 `{code: 200, message, data}`。请求 JSON **snake_case**（与现有 `PUT /me` 一致，不要搞 camelCase 别名）。

### 5.1 一览

| 方法 | 路径 | 鉴权 | 说明 |
|------|------|------|------|
| PUT | `/api/auth/password` | 管理员 | 校验旧密码后改密 |
| POST | `/api/auth/email/code` | 管理员 | 向**新邮箱**发 6 位验证码 |
| PUT | `/api/auth/email` | 管理员 | 校验验证码后写入 `user.email` |
| PUT | `/api/auth/me` | 管理员 | **不再接受 email**，其余字段不变 |

路由顺序：静态路径 `password`、`email/code`、`email` 写在现有 `/login`、`/me` 旁边即可，没有 `/{slug}` 陷阱。

### 5.2 PUT `/api/auth/password`

`ChangePasswordRequest`：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| old_password | string | 是 | 当前明文密码 |
| new_password | string | 是 | 新明文密码，`min_length=8` |

确认新密码只在前端比一次，**不要**进请求体。

成功：`{code: 200, message: "密码已更新", data: null}`。当前 Token 继续有效。

失败（本接口多出来的）：

| HTTP / code | message | 何时 |
|-------------|---------|------|
| 400 | 旧密码错误 | 旧密码对不上 |
| 400 | 新密码不能与旧密码相同 | 新旧明文相同 |
| 422 | 参数校验失败 | 缺字段，或新密码不足 8 位 |

旧密码错误不要写成登录那句「用户名或密码错误」（那是防枚举；这里人已经登录）。也不要 401，避免前端误判掉线。

### 5.3 POST `/api/auth/email/code`

`SendEmailCodeRequest`：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| email | string | 是 | 要绑定的新邮箱 |

格式：含 `@` 且本地部分、域名都不为空即可（service 里判，或 Field pattern）。不要引入 `EmailStr`。

成功：`{code: 200, message: "验证码已发送", data: null}`。**响应里禁止带回验证码。**

行为：

1. 邮箱格式不合法 → 400 `邮箱格式不正确`
2. 与当前 `user.email` 相同（忽略大小写、去首尾空格）→ 400 `新邮箱与当前邮箱相同`
3. 同一用户 60 秒内重复发 → 400 `验证码发送过于频繁`
4. SMTP 未配置 → 500 `邮件服务未配置`
5. 发送失败 → 500 `验证码发送失败`
6. 生成 6 位数字，按用户名存内存，绑定这次的目标邮箱，10 分钟过期；新发覆盖旧码

验证码发到**新邮箱**（证明能收信），不是旧邮箱。首次绑定、更换都走这一条。

### 5.4 PUT `/api/auth/email`

`UpdateEmailRequest`：

| 字段 | 类型 | 必填 |
|------|------|------|
| email | string | 是 |
| code | string | 是 |

成功：`{code: 200, message: "邮箱已更新", data: null}`。写 `user.email` 和 `updated_at`，用完删码。

失败（本接口多出来的）：

| HTTP / code | message | 何时 |
|-------------|---------|------|
| 400 | 邮箱格式不正确 | 格式不合法 |
| 400 | 验证码错误或已过期 | 无记录、过期、code 不对、email 与发码时不一致 |

过期和填错用同一句，避免试探。校验通过后再查用户、落库。

### 5.5 PUT `/api/auth/me` 变更

`UpdateUserInfoRequest` 只保留：`nickname`、`bio` / `description`、`avatar`。

前端若仍传 `email`，Pydantic 默认忽略多余字段，**不得**再写入。文档和后台都按「邮箱只能走 `/email`」交接。

## 6. 验证码存储

单人后台，**进程内 dict**，不建表、不上 Redis。

建议结构：`username → {email, code, expire_at, sent_at}`。

- 进程重启码作废，用户再点发送即可
- uvicorn 多 worker 时各进程各算一份，本期按单进程用；不要为此上 Redis
- 用完、过期都删掉，避免旧码残留
- 不要把验证码打进日志

并发：发码 / 校验用 `threading.Lock` 包一下 dict 即可。

## 7. SMTP

标准库 `smtplib`，路由保持 **sync**（与现有 Auth 一致）。工具函数：`send_verify_code_email(to: str, code: str) -> None`，失败抛错，由 service 转成 500。

`.env`：

```
SMTP_HOST=smtp.qq.com
SMTP_PORT=465
SMTP_USER=
SMTP_PASSWORD=
SMTP_FROM=
```

| 项 | 说明 |
|----|------|
| `SMTP_PASSWORD` | QQ / 163 **授权码**，不是登录密码 |
| `SMTP_FROM` | 可与 `SMTP_USER` 相同；未配则用 `SMTP_USER` |
| 未配 HOST 或 USER | 视为未启用，发码 500 `邮件服务未配置` |
| 端口 465 | SSL；若以后要 587 STARTTLS 再加开关，本期写死 465+SSL 即可 |

邮件正文纯文本即可，例如：`你的验证码是 123456，10 分钟内有效。` 主题：`博客后台邮箱验证`。

`Config.py` 用 `os.getenv`，不要 `os.environ[...]` 强制必填（没配 SMTP 时应用仍能启动，只是发码失败）。

## 10. 验收

1. 无 Token `PUT /password` → 403  
2. 错旧密码 → 400 `旧密码错误`，库里哈希不变  
3. 新密码少于 8 位 → 422  
4. 新旧相同 → 400 `新密码不能与旧密码相同`  
5. 改密成功后，**原 Token** 仍能调 `GET /me`；用新密码能重新登录，旧密码不能  
6. `PUT /me` 带 `email` 成功，但 `GET /me` 的 email **不变**  
7. 未配 SMTP 发码 → 500 `邮件服务未配置`  
8. 合法新邮箱发码 → 200，收件箱有 6 位数字；接口 body 无 code  
9. 60 秒内再发 → 400 `验证码发送过于频繁`  
10. 错码 / 过期码 / 邮箱与发码不一致 → 400 `验证码错误或已过期`  
11. 正确码 → `GET /me` 为新邮箱；同一码再提交失败  
12. 发到当前已绑定的同一邮箱 → 400 `新邮箱与当前邮箱相同`  
13. GitHub Token 调这三条 → 401 `无效的令牌`（或解得出来但不是本模块用户，按现有 `get_current_user` 行为，不要另开访客鉴权）

第 13 条：管理员 `decode_token` 成功即过；GitHub JWT 无 `sub` 当用户名去查 `user` 会 404。验收时带 GitHub Token 调即可，记下实际 message，写进 modules。

## 11. 易错点

- 成功 `code=200`，不要写成学习稿里的 0。  
- 改密失败用 **400**，不要 401，以免后台清 Token。  
- `PUT /me` 必须停止写 email，否则验证可被绕过。  
- 验证码只进邮件，不进 JSON、不进日志。  
- 内存码按 **username** 存，校验时 email 必须与发码时一致。  
- `hash_password` 与登录同一套 bcrypt；不要改成 passlib 另一套算法。  
- SMTP 授权码走环境变量，不要写进仓库。  
- 前端确认密码不传后端；后端只认 `old_password` / `new_password`。
